# 「挑」这一层 —— 从「能执行」到「会挑」

> 2026-11-04 · 调研 + 设计稿 · 不是实现，先对齐再动手
> 现状基线：`PANEL_BUILD = 27`，33 个工具，`node tools/check.mjs` 全绿。

---

## 0. 一句话

现在的插件**会干活，但不会看**。你让它回、它回；你让它发，它发。
你要的「看到好看的叫我」缺的不是一个开关，是**中间那一层：候选 + 判据**。

---

## 1. 调研：抄哪一段，不抄什么

抄项目很容易抄成「四不像」，因为抄的是结果态。所以这张表只写**能搬进这个仓库的那一段**。

| 项目 | 抄这一段 | 落在哪 | 不抄 |
|---|---|---|---|
| **paopaojun/Douyin_Curation_Assistant**<br>Vue3 + Express + sqlite + playwright-core | ① 「刷」和「动」分开，中间隔一层**候选库**<br>② **创作者画像**：作者维度沉淀（粉丝/高赞作品/高频话题）<br>③ **浏览器实验室**：独立 profile + 动作抓包/回放 | `lib/picks.mjs`（新）<br>`lib/taste.mjs`（新）<br>`tools/lab.mjs`（可选） | Vue / Element Plus / sqlite（宿主无构建、零依赖） |
| **NanmiCoder/MediaCrawler**（64k★） | ① CDP 复用真实浏览器上下文（我们已在做，可对照它的登录态缓存）<br>② 「统一入口 + 平台分发」的收口方式 | 已在 `lib/cdp.mjs`；分发层暂不做 | Python / uv / 代理池 |
| **douyin-mcp**（Playwright MCP） | ① **动作级限流常量**：`MIN_INTERVAL` / `DAILY_LIMIT` 写进动作本身<br>② 工具名用**动词**（`like_video`），不是名词<br>③ `browse_for_recommendations`：只负责刷+列清单，判断交给上层 | 工具命名（本轮不改，记账）<br>`lib/picks.mjs` 的 collect 语义 | Playwright（宿主是 CDP） |
| **dsh-douyin-watch**（同类 DSH 插件） | **事件驱动**：有私信就唤醒 agent，而不是每 N 分钟轮询 | 第二阶段，见 §8 | 它的 cookie 落盘方式（我们已有 icacls 收紧） |

## 2. 三个真缺口（核对过代码，不是猜）

| # | 缺口 | 证据 |
|---|---|---|
| 1 | **点赞 / 收藏 / 关注 三个写动作根本不存在** | `lib/api.mjs` 只有 `self/works/detail/comments/likes/notices/searchVideo/deleteComment/reply`。`likes` 是**读**别人的喜欢列表，不是点赞 |
| 2 | **候选库缺失** | `feed-seen.json` 只存 id 做去重（`lib/feed.mjs` `saveSeen`），作品本体（desc/作者/数据）刷完即弃。所以「昨天刷到那个好看的」找不回来 |
| 3 | **口味模型缺失** | 只有 keywords 白名单 + block 黑名单 + minDigg。这是**筛**，不是**懂** |

`feed.mjs` 头部注释写得很清楚：「只读：不点赞、不关注、不评论」。这条边界当时是对的（防手滑），
但你要的「人有的他都有」必须跨过去 —— 所以下面 §7 单独讲怎么跨得安全。

## 3. 数据模型：`picks.json`

一个文件，一份数组，不引数据库。

```jsonc
{
  "updatedAt": "2026-11-04T21:00:00Z",
  "items": [{
    "aweme_id": "7...",          // 唯一键
    "desc": "…",                  // 前 200 字
    "author": "辰辰辰chen",
    "sec_uid": "MS4w…",           // 认人，不靠昵称
    "duration_sec": 32,
    "digg": 12400, "comment": 380, "share": 210,
    "cover": "https://…",         // 面板要用（外部图，加载失败就退成色块）
    "source": "search:露营",      // 从哪来的：search:<词> / recommend / creator:<sec_uid>
    "score": 0.62,                // 0–1
    "why": "同一作者你看过 3 次",  // 得分最高的那个特征，一句话
    "state": "new|seen|liked|saved|sent|dismissed",
    "first_seen": "…", "notified_at": "…"
  }]
}
```

上限 300 条，FIFO 淘汰 `dismissed` 优先。写入走 `lib/fsx.mjs` 的 `atomicWriteJson`（坏文件隔离已有）。

## 4. 打分：零依赖、可解释

不训练模型。**用你自己的历史当正样本** —— 这些标签你已经有了，不用填任何东西：

| 正样本来源 | 现成读数 |
|---|---|
| 点赞过的 | `api.likes()`（自己） |
| 发过的作品 | `publishes.json` |
| 回过的评论所在的作品 | `ledger.json` |
| 关注的人 | 作者列表 |

特征（每项归一到 0–1，加权求和）：

| 特征 | 权重 | 说明 |
|---|---|---|
| 作者重合 | 0.30 | 出现在正样本作者集里 → 1；同话题作者 → 0.5 |
| 话题重合 | 0.25 | tags / desc 与 `keywords` + 正样本高频词的交集 |
| 互动率 | 0.20 | `digg / max(粉丝,1)`，取分位数；比绝对点赞数公平 |
| 时长贴合 | 0.15 | 落在你历史看的时长区间（`minSec`–`maxSec` 内再收紧） |
| 新鲜度 | 0.10 | 24h 内满分，7 天线性衰减 |

**`why` 必须能生成。** 分数本身对用户没意义，一句话才有：取贡献最大的那个特征，翻成人话。
> 「同一作者你看过 3 次」「话题「露营」你回过 5 条」「互动率是同类 92 分位」

这一条是设计约束不是锦上添花：**给不出理由就不该叫你**。

## 5. 「叫我」的三条曲线

你要的「一天几轮、每轮多少、什么类型、看到好的叫我」其实是三件事：

| 曲线 | 设置项 | 默认 |
|---|---|---|
| 频率 | 每天几轮 | 3 |
| 广度 | 每轮刷几条 | 12 |
| 阈值 | 多好才值得叫你 | 0.6 |

**关键：让「叫我」有成本。** 如果每轮都 at，第三天你就会关掉它。所以：

- 每天最多叫你 `notifyPerDay` 次（默认 2）；用完只入库不通知
- 三档，不是一个动作：**入库**（值得留）→ **@ 你**（值得现在看）→ **私信**（想让你回一句）
- **沉默也是信息**：连续 3 天没有候选过线 → 明确说「今天没有值得看的」，不硬凑
- 被 `dismissed` 的作者/话题权重降 0.2，连续 3 次 → 拉黑（可撤销）

这条原则和仓库里那条「宁可给 2 分钟前的列表，也不让人盯着转圈」是同一条哲学：**宁可不叫**。

## 6. 界面：三动作 + 一张「挑」

沿用 `docs/ui-redesign.md` 的方案 C 骨架，但把入口收敛成三个：

```
看板：今天还能发 36 条 · 叫了你 1/2 次
[待办 3] [挑 5] [今天]
```

「挑」是新的主角，一屏 3–5 条，每条一行高：

```
┌─────────────────────────────────────────────────────┐
│ [封面] 露营装备清单｜这条能省 3000 块        0.72    │
│        同一作者你看过 3 次 · 32 秒 · 1.2 万赞        │
│                            [赞] [存] [发我] [×]      │
└─────────────────────────────────────────────────────┘
```

- 四个按钮里只有「发我」是实底 —— 其余三个是次级（沿用 b13 的「一屏一个主按钮」）
- `[×]` = dismissed，直接参与口味负反馈
- 不需要新接口：`GET /picks` + `POST /picks/act`（act 里带 `like|save|send|dismiss`）

## 7. 额度：三个新出口（⚠️ 需要你点头）

`lib/budget.mjs` 在 `HANDOFF.md` 里是**禁改区**（「改错不是不好用，是掉登录或封号」）。
点赞/收藏/关注要出门，就必然要加闸。建议：

```js
CHANNELS += ['like', 'save', 'follow']
perDay:    { like: 30, save: 10, follow: 5 }
perHour:   { like: 10, save: 4,  follow: 2 }
minGapSec: { like: 20, save: 30, follow: 60 }
```

保守到「一天 30 个赞」看着很抠，但这是**第一次跑真实互动的起始值**，跑一周没异常再抬。
`totalPerDay` 不含这三项（它们不是消息）。fail-closed 语义照旧。

**这条我不能自己改。** 你说行，我再动，并且单独跑一版 `budget` 测试。

## 9. 明确不做

- **不做无限下滑**。刷是为了挑，不是为了陪伴。
- **不做「AI 帮你评论别人」**。回评论只在「你的作品下」和「@ 你」两个场景，这是账号存续的边界。
- **不做多账号**。一个号已经够复杂了。
- **不引依赖**。零依赖是这个仓库能活 27 个版本的原因。
